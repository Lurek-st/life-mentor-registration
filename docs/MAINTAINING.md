# 维护与公开发布

这是通用开源代码仓库，不是任何组织的运行数据或云账户备份。

## 下次同步功能

1. 在功能分支记录来源版本及要移入的功能，只选择 `src/`、`worker/`、`shared/` 中相关代码；逐项处理 `schema/` 和迁移。
2. 保留本仓库的通用配置、虚构模板、本机测试保护、许可证、部署示例和 CI。机构文档、现场记录、个人资料、真实配置、口令及整个运行目录都不导入。
3. 新字段同时更新导出、加密备份、恢复工具及旧版迁移测试。新工号或邮箱规则必须前后端一致。工号与实际到场是不同概念，不靠报名推定出席。
4. 更新 README、操作说明、CHANGELOG 和虚构截图。开源版本独立编号；不要把未发布版本写成已发布。
5. 先获取实际准备发布的完整分支及标签历史，再暂存明确文件清单并运行 `npm run check:public`。它扫描 Git 索引和本机所有可达提交，即使敏感文件已从当前版本删除，也会检查旧内容；浅克隆会被拒绝。提交后从全新目录重建和测试，验证不存在对忽略文件的依赖。
6. 提交 PR，等待 CI 成功后再合并并发布版本。仓库主分支应要求 PR 和 `verify` 检查通过，禁止强推和删除；单人维护可将必须审核人数设为 0。CI 获取完整历史，只做本机验证，不持有部署密钥。若仓库由托管平台自动部署，发布前先核实其外部连接，避免误改正在使用的站点。

## 两轮审查

- 第一轮：实现与数据。类型、构建、API、竞争最后一席、重复提交、后台纠错、到场核对、Excel、真实升级与备份恢复。
- 第二轮：公开交付与使用。新目录从零安装、手机和桌面操作、双语、减少动效、网络失败、权限边界、提交内容和 Git 历史的敏感信息检查。

自动检查只覆盖常见凭据模式、部署绑定和文件边界，不能证明没有所有种类的秘密或个人资料。图片必须人工查看；历史检查只覆盖已获取的可达提交，不覆盖未获取的远端分支、已丢失引用的对象或第三方克隆。发现泄漏应先撤销对应凭据，再处理历史，不能只删当前文件。不要只依赖 `.gitignore` 或 GitHub 的自动密钥拦截。

新测试只能使用合成资料与独立本机数据库；不能指向真实报名网站。日志和截图放在忽略的 `work/`，公开图片另外挑选无身份信息的示例。
